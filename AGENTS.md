# SwoleMates working rules

- Preserve existing user data and teammates' work. Do not use destructive commands, reset databases, drop or truncate tables, bulk delete records, overwrite unrelated changes, or force push. If a task appears to require an irreversible operation, stop before that operation and propose a safer path.
- Keep Supabase data organized by domain. Start with `docs/DATA_MODEL.md` and the team's Supabase table rules in `.cursor/rules/supabase-tables.mdc` on `main`. Confirm the existing schema and access paths with the database owner before planning schema changes. Reuse existing domain tables and avoid duplicate tables, views, or new catch-all payloads. Propose a new table only when the existing schema cannot hold the data, and document why. Leave existing storage and records intact unless a separate migration has been reviewed and approved.
- Protect CPU and database capacity. Keep queries, result sets, retries, polling, and concurrency bounded. Avoid full-table reads or rewrites on user-facing paths, per-row query loops, and redundant refreshes. Check affected query plans and test with representative data in a local or staging environment before proposing a database or performance-sensitive change.
- Before committing or pushing a database-related change, review the diff, migration ordering, compatibility with existing clients, and any deployment hooks the push could trigger. Prefer additive migrations and validate them away from production. Do not apply migrations, run backfills, or deploy database changes to a shared or production Supabase project without explicit authorization for the target and operation.
